# seiso 设计与实施方案

Sep 27, 2026 · @ScarletKc

## 背景与定位

seiso 是一个用 Rust 编写、手感对标 ruff 的 Markdown 文档 linter。它检查文档会不会腐烂，不检查措辞像不像 AI。

AI 写文档的速度远超人工审阅，而且失败模式高度重复：

- 把会变的值写死在长期文档里：版本号、部署状态、数量。
- 同一组字段复制到多个页面，再补一句 "see X for details"。
- 在 how-to 里插一段设计论证，把读者要的步骤挤到下面。
- 产出里残留生产过程：放弃的方案、"本页演示了"、"下一步我们可以"。

seiso 是一个独立的规则器。规则、说明和示例都随工具发布，不依赖任何 skill 或 prompt：同样的输入永远得到同样的结果，非零退出码能挡住 CI，agent 只读诊断就知道哪里错、怎么改。

规则的出发点来自 [ux-writing skill](https://github.com/scarletkc/agents/tree/main/skills/ux-writing) 里总结的文档问题。skill 是写作时的建议，模型可以不照做，写完也没有东西验证；seiso 把能判定的部分做成硬性检查。两者各自维护、互不依赖，只装 seiso 也能完整使用。

### 与现有工具的分工

| 工具 | 检查对象 | 与 seiso 的关系 |
| --- | --- | --- |
| markdownlint | 格式：标题层级、列表缩进、行长 | 互补，seiso 不做格式检查 |
| Vale、textlint | 风格与用词 | 互补 |
| [slopless](https://github.com/agent-quality-controls/slopless)、[ai-slop-linter](https://github.com/Bubblegunn/ai-slop-linter) | AI 腔措辞：特定词汇、句式、破折号 | 不竞争，措辞换个同义词就能绕过 |
| lychee 等链接检查器 | 外部链接是否可达 | 互补，seiso 只检查仓库内的相对链接和锚点 |

seiso 自己的范围是文档结构与事实归属：过期值、重复事实、指向不明、职责混杂、生产过程残留。

### 非目标

- 不判断文字是不是 AI 写的。
- 不做格式、拼写和语法检查。
- 不内置生成式模型，不自动改写语义；语义修复交给写文档的人或 agent。
- 第一版不提供插件系统，规则全部内置。

## 需求

第一版的底线有三条：默认规则几乎不误报，单文件检查快到可以挂在每次编辑后，结果完全可复现。

### 目标用户与场景

| 用户 | 场景 | 入口 |
| --- | --- | --- |
| 用 coding agent 写文档的开发者 | agent 每次写入或修改 .md 后自动检查，报错回传给 agent 自行修复 | Claude Code hook |
| 开源项目维护者 | PR 里的 docs 改动自动检查，挡住重复和过期内容 | GitHub Actions、pre-commit |
| 文档负责人 | 给已有文档库做一次体检，按规则统计问题分布 | `seiso check --statistics` |

### 功能需求

1. 解析 CommonMark、GFM 和 YAML frontmatter，所有诊断带精确的行列位置。
2. 支持两类规则：单文件规则，和依赖全仓索引的跨文件规则。
3. 每篇文档声明自己的 kind，规则按 kind 生效；未声明时按路径映射推断，仍无法确定就报错。
4. 规则可按前缀或编号 select / ignore，并支持按路径覆盖。
5. 支持块级和文件级 suppression，每条都必须写理由。
6. `--fix` 只做不改变语义、且前提能被完整验证的修复。
7. 输出人类可读文本、JSON、SARIF 和 GitHub 注释；退出码区分“有违规”和“工具出错”。
8. 每条规则都有说明文档，包含触发条件、正反例和处理建议。

### 非功能需求

| 项目 | 目标 |
| --- | --- |
| 确定性 | 同一仓库快照、同一版本、同一配置，输出逐字节一致，与缓存状态无关；默认规则不联网 |
| 精度 | stable 规则在评估语料上的误报率 ≤ 5%，即 precision ≥ 95%；按规则分别计算，以留出集结果为准，样本不少于 100 条已标注诊断。KND002、SUP001、SUP002 适用下文的协议规则验收例外 |
| 速度 | hook 场景的带路径检查 < 150 ms，1,000 个文件全量检查 < 1 s；场景与测量条件以「质量保障」的性能基准为准 |
| 分发 | 单个静态二进制，可通过 cargo、pip（uvx）、npm（npx）安装 |
| 语言 | 规则同时覆盖英文、中文、日文正文 |
| 可解释 | 只看诊断输出就知道问题在哪、该怎么改，不依赖任何 skill 或外部文档 |
| 稳健 | 任何输入都不 panic；个别文件读取失败时继续检查其余文件，但本次检查记为不完整，退出码为 2 |

## 核心概念

seiso 不去猜作者的意图：它要求作者把判断写出来，再检查文档是否与声明一致。这和 import-linter 管架构的思路相同：分层由人声明一次，工具负责让它一直成立。

### kind 声明

每篇文档声明自己的职责。只有先说清楚一篇文档负责什么，才判断得了某个事实该归哪一页、哪些内容放错了地方。

```yaml
---
kind: howto
---
```

| kind | 回答的问题 | 允许 | 不允许 |
| --- | --- | --- | --- |
| `readme` | 这是什么、怎么开始 | 定位、快速开始、指向文档的链接 | 字段表、架构细节、当前版本号 |
| `howto` | 怎么做 | 步骤、命令、预期结果 | 设计论证、完整选项参考 |
| `reference` | 有什么 | 表格、定义、取值 | 操作步骤、历史 |
| `runbook` | 出事时怎么处理 | 检查命令、处置步骤 | 当前部署状态、版本号快照 |
| `adr` | 为什么这样设计 | 背景、决定、取舍、日期 | — |
| `plan` | 接下来要做什么 | 阶段、日期、状态 | 被长期文档当作规范引用 |
| `changelog` | 发生了什么 | 日期、版本号、提交 | — |
| `generated` | 由工具生成 | 由生成器负责 | 不运行规则，但仍进入索引，可作链接目标和归属方 |

下文把 `readme`、`howto`、`reference`、`runbook` 合称“长期文档”。kind 也可以在配置里按路径批量指定，frontmatter 优先；但 generated 只能在配置里指定，防止文件自行豁免检查。无法确定 kind 时的处理见「执行语义」。

声明 kind 就是接受上表的内容契约。kind 声明不了某个版本号是否已经过期，所以规范类规则只检查文档有没有违反契约，不断言内容本身已经过期或错误。

### 判断显式化

有些问题只有人能判断，比如一段论证是不是“下一个读者自己推不出来的约束”。seiso 把这类判断变成一行可 review 的记录：

```markdown
<!-- seiso: allow RAT001 -- 签名校验要求保持 key 顺序 -->
```

没有理由的 suppression 本身就是违规；确认已经失效的 suppression 也是（语法和失效判定见「执行语义」）。理由会进入 `--statistics` 的输出，方便定期回看哪些豁免已经过时。

### 规则分级

规则只有启用和关闭两种状态，没有 warning。这一点跟 ruff 一致：warning 会堆积成噪音，最后没人看。

| 级别 | 含义 | 默认 |
| --- | --- | --- |
| stable | 在留出集上达到「需求」里的精度目标，行为由快照测试锁定 | 启用 |
| preview | 启发式规则，或精度数据还不够 | 关闭，`--preview` 开启 |
| judge | 需要外部分类模型 | 关闭，见「后续：判断层」 |

新规则一律先进 preview。一致性和规范类规则在留出集上达标后升为 stable；启发式规则默认留在 preview，精度和使用噪声都达标才升级（分类见「规则体系」）。

KND002、SUP001、SUP002 检查 seiso 自己引入的声明协议，可以通过协议一致性验收升为 stable：正反例、非法输入、作用范围与优先级、规则未启用与检查不完整状态、确定性和源码位置全部通过，并确认未修改的真实留出集没有误触发。构造样例单独报告，不计入自然语料的精度或样本量；没有自然诊断时，precision 记为无法计算。KND001、LNK001 和所有规范规则仍须满足上表的留出集样本量与精度门槛。验收依据见[协议规则验收决定](evaluation/m1-gate-proposal.md)。

## 规则体系

首批规则 27 条，分属 12 个前缀族。按判定依据分为一致性 6 条、规范 6 条、启发式 15 条；前两类是默认启用的候选，启发式规则默认留在 preview。规则编号 = 三个字母的前缀 + 三位数字。

### 前缀族

| 前缀 | 含义 | 要解决的问题 |
| --- | --- | --- |
| KND | kind 声明 | 文档没说清自己负责什么，就无法判断内容放错了没有 |
| STL | 过期事实 | 会变的值写进长期文档，过一阵就变成错的 |
| PTR | 指向不明 | `见源码`、指向仓库根目录的链接，读者还得自己找 |
| LNK | 仓库内链接 | 文件或标题改名后，链接和锚点悄悄失效 |
| DUP | 重复事实 | 同一份内容复制到多处，改一处漏一处 |
| OWN | 事实归属冲突 | 两份文档都在定义同一件事，读者不知道信哪份 |
| RAT | 论证放错位置 | 操作文档里夹着“为什么这样设计”，步骤被挤到后面 |
| ORD | 阅读顺序 | 读者最先需要的内容排在后面 |
| MIX | 职责混杂 | 一页同时在教操作、列参考、讲设计 |
| VOX | 生产过程残留 | 成品里留着“本页演示”“根据你的要求”这类制作痕迹 |
| EVD | 无依据的评价 | “推荐”“更快”没有数字或出处支撑 |
| SUP | suppression 本身 | 豁免没写理由，或已经不再需要 |

### 判定依据

| 依据 | 含义 | 默认 | 诊断怎么说 |
| --- | --- | --- | --- |
| 一致性 | 结论可以机械验证：kind 取值非法、链接目标确定不存在、suppression 格式错误 | 达标后启用 | 直接陈述事实 |
| 规范 | 检查是否违反 seiso 的写作规范，包括各 kind 的内容契约；触发条件收窄到几乎只匹配规范禁止的写法 | 在留出集上达标后启用 | 说明违反了哪条规范，不断言内容已经过期或错误 |
| 启发式 | 质量判断：疑似重复、论证过多、顺序不当 | 留在 preview | 只陈述观察到的特征，建议写成条件式 |

三类规则共用一条措辞原则：诊断的语气不能强于证据。只检测到时态词和版本号，就说“长期文档里出现了当前状态的快照”，不说“这个版本已经过期”；只检测到标识符重合，就给条件式建议，不直接要求删除。seiso 的诊断会被 agent 直接执行，这条边界比多实现几条规则更重要。

### 首批规则

| 编号 | 检查什么 | 适用 kind | 依据 | 阶段 |
| --- | --- | --- | --- | --- |
| KND001 | 无法确定 kind：frontmatter 无法解析，或既没有声明 kind 也不匹配路径映射 | 全部 | 一致性 | M1 |
| KND002 | kind 取值不在允许列表中，或在 frontmatter 里声明了 generated（只能在配置中指定） | 全部 | 一致性 | M1 |
| STL001 | 同一句里同时出现时态词（currently、latest、目前、最新、現在）和易变值（版本号、commit hash、镜像 tag、数量），且句中没有约束词（≥、+、or later、at least、以上、要求） | 长期文档 | 规范 | M1 |
| STL002 | 部署状态断言：is live、not yet shipped、已上线、尚未发布；条件句（after、once、确认……后）不报 | 长期文档 | 启发式 | M3 |
| STL003 | 紧跟 commit、sha、build、提交、构建等上下文词的 7–40 位十六进制串；代码块和 URL 除外 | 长期文档 | 规范 | M1 |
| STL004 | 没有约束词的裸版本号 | 长期文档 | 启发式 | M3 |
| PTR001 | 指引句（see、defined in、见、定义在、参照）里的链接指向仓库根目录 | 除 changelog | 规范 | M1 |
| PTR002 | 链接指向目录，且该目录不在 `catalog-dirs` 配置里 | 除 changelog | 启发式 | M2 |
| PTR003 | `see the source`、`见源码`、`ソースを参照`这类指引，句中（含行内代码和链接目标）没有文件路径或符号 | 全部 | 规范 | M1 |
| LNK001 | 相对链接的目标确定不存在；无法判断时不报 | 全部 | 一致性 | M1 |
| LNK002 | 链接锚点在目标文件中确定不存在：标题 slug、重复标题编号、HTML 自定义锚点都不匹配 | 全部 | 一致性 | M2 |
| DUP001 | 同一比较域内，两个文件的定义型列表或表格含同一组反引号标识符（默认至少 5 个，Jaccard ≥ 0.8） | 全部 | 启发式 | M2 |
| DUP002 | 复述后链接：小节以指向 X 的链接收尾，且小节里的标识符大多也出现在 X 的目标小节中 | 全部 | 启发式 | M2 |
| DUP003 | 同一比较域内的近似重复段落（shingle 相似度 ≥ 0.9） | 全部 | 启发式 | M2 |
| OWN001 | 同一组标识符在 plan 和另一份文档里都以定义形式出现（表格首列、定义列表） | 全部 | 启发式 | M2 |
| OWN002 | 归属无法确定：重复内容的双方同为最高优先级，或都声明了 canonical | 全部 | 启发式 | M2 |
| RAT001 | 第一个步骤之前出现论证段（比较、因果标记的密度超过阈值） | howto、reference | 启发式 | M3 |
| RAT002 | 论证设计选择的标题：“Why we chose”“为什么选择”“为什么不用”“なぜ…を選んだ”；排障类问题（“为什么连接失败”）不报 | howto、reference | 规范 | M1 |
| ORD001 | 第一个可运行代码块或有序列表之前超过 30 行，或已有 10 行以上的表格 | howto | 启发式 | M3 |
| ORD002 | 故障排除、FAQ、例外类标题出现在主流程之前 | howto、runbook | 启发式 | M3 |
| MIX001 | 按特征给 section 分类后，与 kind 不符的类型占比超过阈值 | 长期文档 | 启发式 | M3 |
| VOX001 | 对话残留：直接对委托人说话的措辞，如“根据你的要求”“as you requested”“Here's the updated”“希望对你有帮助” | 长期文档 | 规范 | M1 |
| VOX002 | 标题里的否定范围：“(without …)”“（不含…）” | 全部 | 启发式 | M3 |
| VOX003 | 生产过程标题或自我叙述：“Next steps”“实现思路”“本页演示了”“this page demonstrates” | 除 plan、adr | 启发式 | M3 |
| EVD001 | 评价性形容词（recommended、faster、推荐、更快、最佳）附近没有数字也没有链接 | 长期文档 | 启发式 | M3 |
| SUP001 | suppression 无效：缺少理由、编号未知或格式错误 | 全部 | 一致性 | M1 |
| SUP002 | suppression 已失效：相关规则已完整执行，作用范围内却没有可抑制的诊断 | 全部 | 一致性 | M1 |

表中“全部”不含 generated：generated 文件不运行任何规则。kind 无法确定的文件只运行 KND、LNK、SUP 三族（见「执行语义」）。

### 比较域与归属

DUP 和 OWN 只在同一个比较域内比较。比较域 = 语言 × 配置的域：语言取 frontmatter 的 `lang`，没有时按正文字符占比判断（拉丁字母为主是 en；汉字和假名为主时，含假名为 ja，否则为 zh）；域由 `[[domains]]` 按路径划分，未配置时整个工作区是一个域。这样，同一文档的中英文版本不会互相报重复，客户端和服务端的同名字段也可以分开比较。

重复只做两两判定，不做传递合并。对每个重复块，按以下顺序找出排名最高的一方：声明了 `canonical: true` > generated > reference > adr > howto > readme > 其他。诊断报在排名较低的一方，`related` 列出所有排名更高的出处；最高排名出现并列时（同一种 kind 且都没声明 canonical，或都声明了 canonical），并列各方都报 OWN002，要求明确归属。

`canonical` 对整篇文件生效，含义是“与其他文件重复时，以本文件为准”。不采用“最早出现的文件优先”：它要依赖 Git 历史或索引时间，同一快照可能得出不同结果。

### 规则行为约定

- **词表按语言维护。** STL、PTR、RAT、VOX、EVD 的词表分 en、zh、ja 三套，可在配置中扩展。中文和日文直接在字符上匹配，不依赖分词。
- **修复范围。** 第一版不提供自动修复。删除已失效 suppression 的修复在 M2 通过 suppression 状态测试后开放；其余规则的修复都涉及语义，交给写文档的人或 agent。
- **阈值可配置。** 表中的数字是默认值，只在调参集上调整，验收看留出集（见「质量保障」）。

### 规则说明文档

每条规则的说明都用同一个结构，`seiso rule <CODE>` 输出的就是它，读者不需要看任何别的材料。

| 小节 | 内容 |
| --- | --- |
| 检查什么 | 一句话说明触发条件 |
| 依据 | 一致性、规范或启发式；规范类写明对应的规范或 kind 契约 |
| 为什么是问题 | 这个问题让读者付出什么代价，附一个真实场景 |
| 示例 | 会触发规则的写法 |
| 改成 | 修改后的写法 |
| 例外 | 什么情况下该写 suppression，理由怎么写 |
| 读取的内容 | 读取哪些片段类型，是否依赖文件系统或全仓索引 |
| 配置 | 相关的阈值和词表选项 |

诊断文案也要自解释：第一行说问题在哪，`= 建议：` 一行说怎么改。说明文档中的“示例”和“改成”同时作为测试 fixture 运行（见「质量保障」），文档不会和实际行为脱节。

## 架构

每次检查都基于当前仓库快照：缓存只复用解析结果，kind、链接解析和全部规则每次重算。

### 执行顺序

1. 发现文件：遍历工作区，得到当前快照的完整文件清单。每次检查都重新遍历，不靠缓存判断文件是否存在。
2. 读取与解析：读取全部文件并计算内容 hash；命中缓存时复用解析结果和内容事实（标识符、标题、原始链接、suppression 注释），否则重新解析。
3. 解析路径相关信息：kind、比较域、链接目标及其解析状态，并确定每个文件启用的规则。这一步每次重算。
4. 合并全仓索引。
5. 执行规则：单文件规则与跨文件规则，得到原始诊断。
6. 应用 suppression 并记录命中；只对能完整判定的 suppression 运行 SUP002。
7. 按报告范围过滤、排序、输出；需要时生成安全修复。

### 模块划分

项目使用一个 `seiso` Cargo package，包含库和 CLI；内部按模块划分职责。

| 模块 | 职责 |
| --- | --- |
| `main`、`commands` | 命令行入口、子命令、输出渲染 |
| `config` | 发现并合并配置：`seiso.toml`、`.seiso.toml`、`pyproject.toml` 的 `[tool.seiso]` |
| `md` | 用 markdown-rs 解析，转成 seiso 文档模型 |
| `index` | 构建全仓索引：合并内容事实与路径相关信息 |
| `rules` | 规则实现、各语言词表、规则说明文档 |
| `diagnostics` | 诊断、修复及其适用性（safe / unsafe）的数据结构 |
| `cache` | 按内容 hash 缓存解析结果与内容事实 |

### 文档模型

规则不直接操作 mdast，而是读 seiso 自己的文档模型，换解析器时规则代码不受影响。文档模型包含：

- frontmatter 与解析后的 kind；
- section 树：标题层级、锚点、每个 section 的起止位置；
- 块列表：段落、列表、表格、代码块、引用、HTML 注释；
- 句子：正文按句切分，每句由片段组成（普通文本、行内代码、链接文本、链接目标），并标注语言（en / zh / ja）。

每条规则只读取它声明的片段类型。例如 STL001 同时读普通文本和行内代码，“目前使用 `v1.2.3`”里的版本号不会漏掉；PTR003 会看行内代码和链接目标，“见源码 `src/config.rs`”不会被误报。

所有片段都保留源码字节区间，诊断位置从源码区间换算：行从 1 开始，列按 Unicode 字符计，JSON 另给字节偏移。中日文、转义字符和 Markdown 标记混排时，位置不会因为文本处理而偏移。

### 链接解析

链接目标的解析结果只有三种：存在、确定不存在、无法判断。LNK 规则只对“确定不存在”报错，外部 URL 不检查。

- 路径：相对路径相对于当前文件；以 `/` 开头的路径相对于工作区根；查找前先做百分号解码。
- 引用式链接先找到定义再解析；没有定义的引用在 CommonMark 里不是链接，不处理。
- 锚点：按 GitHub 规则从标题生成 slug，重复标题依次加 `-1`、`-2`；HTML 元素的 `id` 和 `<a name>` 也算有效锚点。
- 记为无法判断的情况：目标在工作区之外；目标被排除出索引（只能确认文件存在，锚点未知）；链接里含模板变量。

### 全仓索引

| 索引 | 内容 | 使用者 |
| --- | --- | --- |
| 标识符 | 行内代码中形如标识符的字符串 → 所在文件、section、块类型（列表、表格首列、段落） | DUP001、DUP002、OWN001、OWN002 |
| 锚点 | 文件 → 标题 slug（含重复标题编号）与 HTML 自定义锚点 | LNK002 |
| 链接图 | 文件 → 出链：原始写法、解析结果、解析状态 | LNK001、LNK002、PTR002、DUP002 |
| 文件属性 | 文件 → kind、比较域、canonical 标记 | 全部跨文件规则 |

### 规则接口

单文件规则和跨文件规则各有一个 trait：前者拿到文档模型，后者额外拿到只读的全仓索引。两者都只返回诊断、不修改任何状态，所以可以安全地并行；输出前按（文件路径、行、列、规则编号）排序。

每条规则还要声明读取的片段类型，以及是否依赖文件系统和全仓索引。执行器据此判断一条规则对某个文件是否完整执行，这是 SUP002 判定的前提。

## 执行语义

同一个仓库快照，无论缓存处于什么状态、从哪个路径发起检查，得到的诊断集合都相同；检查路径只决定报告其中哪些诊断。

### 工作区与范围

| 概念 | 约定 |
| --- | --- |
| 工作区根 | 所用配置文件所在的目录；没有配置文件时，取最近的含 `.git` 的上级目录；都没有时取当前目录 |
| 索引范围 | 工作区内被 include 选中、未被 exclude 和 `.gitignore` 排除的 Markdown 文件；每次检查都重新遍历，新增、删除、重命名自然生效 |
| 检查范围 | 不带路径时为全部索引文件；带路径时，单文件规则只在给定文件上运行，跨文件规则仍基于完整索引计算 |
| 报告范围 | 带路径时，报告主位置在给定文件内的诊断，以及 `related` 涉及给定文件的跨文件诊断。例如改了一个标题，引用它的其他文件里的 LNK002 也会报告 |
| stdin | `--stdin-filename P` 读入的内容在本次检查中替代磁盘上的 P，也参与索引；不写回磁盘 |

带路径检查的结果，必须等于全量检查结果按报告范围过滤后的子集。这条等式是跨文件规则最核心的回归测试。

### 文件角色

| 文件 | 运行规则 | 进入索引 | 作为链接目标 |
| --- | --- | --- | --- |
| 普通 Markdown 文件 | 是 | 是 | 是，可校验锚点 |
| kind 为 generated | 否 | 是 | 是，可校验锚点 |
| kind 无法确定 | 只运行 KND、LNK、SUP | 是，归属优先级最低 | 是，可校验锚点 |
| 被 exclude 或 `.gitignore` 排除的文件 | 否 | 否 | 只校验存在，锚点记为无法判断 |
| 非 Markdown 文件 | 否 | 否 | 只校验存在 |

“不检查一个文件的内容”和“不把它当作链接目标或索引来源”是两回事：generated 文件不被检查，但仍然可以是链接目标和重复内容的归属方。

### 缓存

- 缓存只存内容推导的数据：解析结果，以及标识符、标题、原始链接写法、suppression 注释等内容事实。key = 文件内容 hash + seiso 版本。
- 与路径、kind、文件系统有关的数据一律不进缓存，每次重算：kind、比较域、链接解析与存在性检查，以及全部诊断。同一份内容换了路径，结果按新路径重新计算。
- 每次检查都读取索引范围内的全部文件并计算 hash，不用修改时间判断文件是否变化。
- 缓存缺失、版本不符或无法读取时，直接丢弃并重算，不报错。写入采用“临时文件 + 原子重命名”，多个进程并发检查互不破坏；`--no-cache` 完全绕过缓存。
- 验收：同一快照在冷缓存、热缓存、禁用缓存三种状态下，输出逐字节一致。

### 配置与规则启用

1. 每个文件使用离它最近的配置；同一目录下的优先级为 `.seiso.toml` > `seiso.toml` > `pyproject.toml`（仅当其中有 `[tool.seiso]`）。上级配置不会被隐式合并，需要继承时写 `extend = "<路径>"`。
2. 命令行参数覆盖配置：`--select` 替换 select，`--extend-select` 追加，`--preview` 打开 preview 模式。
3. 规则启用按顺序计算：从 select 出发（默认为全部规则）→ 用 ignore 去掉（编号级条目优先于前缀级；级别相同时 ignore 优先）→ 非 preview 模式下去掉 preview 规则 → 按 per-file-ignores 去掉 → 按 kind 适用性去掉。suppression 在诊断产生之后才生效。
4. kind：frontmatter 优先；否则按 `[[kinds]]` 的书写顺序匹配路径，最后一条命中者生效。generated 只能由配置指定。
5. 比较域：`[[domains]]` 同样按书写顺序匹配，最后一条命中者生效。

这些配置决定了检查有多严格，因此也是 agent 绕过检查的途径：把文件映射成 generated、扩大 ignore、改路径映射。`seiso policy` 输出生效后的策略，CI 用它把策略变化单独展示在 review 中（见「集成」）。

### suppression 语法

| 写法 | 作用范围 |
| --- | --- |
| 独占一行的 `<!-- seiso: allow CODE, CODE -- 理由 -->` | 紧随其后的一个块：段落、列表、表格、代码块或标题 |
| 同样的注释写在段落、列表项或表格单元格内部 | 该段落、列表项或单元格 |
| `<!-- seiso: allow-file CODE -- 理由 -->`，位于 frontmatter 之后、第一个内容块之前 | 整个文件 |

- 只接受完整编号，不接受前缀；编号未知、缺少理由或格式错误都报 SUP001。
- 代码块和行内代码里的注释只是示例，不生效。
- suppression 只匹配诊断的主位置；块级和文件级同时命中时，记在块级上。

### suppression 状态

| 状态 | 条件 | SUP002 |
| --- | --- | --- |
| 有效 | 相关规则已执行，并抑制了至少一条诊断 | 不报 |
| 已失效 | 相关规则对该文件已完整执行，作用范围内没有可抑制的诊断 | 报告 |
| 未判定：规则未启用 | 规则被 select、ignore、preview、per-file-ignores 或 kind 适用性排除 | 不报 |
| 未判定：检查不完整 | 规则依赖的输入不完整，例如跨文件规则需要的某个文件读取失败 | 不报，也不自动删除 |

只有“已失效”的 suppression 才能被 `--fix` 删除；这个修复在 M2 通过上述状态的回归测试后开放。

## 配置、CLI 与输出

配置、命令和输出格式参照 ruff 的约定，用过 ruff 的人不用重新学；具体采用了哪些规则，以「执行语义」为准。

### 配置

配置的查找、优先级和规则启用顺序见「执行语义」。不写 `select` 时选中全部规则；非 preview 模式下，实际生效的只有其中的 stable 规则。

```toml
include = ["**/*.md"]
exclude = ["vendor/**"]
preview = false

# kind 映射：按书写顺序匹配，最后一条命中者生效
[[kinds]]
path = "docs/**"
kind = "howto"

[[kinds]]
path = "docs/reference/**"
kind = "reference"

[[kinds]]
path = "docs/adr/**"
kind = "adr"

[[kinds]]
path = "docs/api/generated/**"
kind = "generated"

[[kinds]]
path = "README.md"
kind = "readme"

[[kinds]]
path = "CHANGELOG.md"
kind = "changelog"

# 比较域：DUP 和 OWN 只在同一个域、同一种语言内比较
[[domains]]
path = "docs/client/**"
name = "client"

[[domains]]
path = "docs/server/**"
name = "server"

[lint]
select = ["ALL"]
ignore = ["PTR003"]
languages = ["en", "zh", "ja"]

[lint.per-file-ignores]
"docs/legacy/**" = ["DUP"]

[lint.dup]
min-identifiers = 5
min-jaccard = 0.8

[lint.ptr]
catalog-dirs = ["locales/", "migrations/"]

[lint.lexicon.zh]
extend-stale-markers = ["截至目前"]
```

### 命令

| 命令 | 作用 |
| --- | --- |
| `seiso check [PATH...]` | 检查整个工作区；带路径时只报告与这些文件相关的诊断（见「执行语义」） |
| `seiso check --fix` | 应用安全修复，M2 起提供 |
| `seiso check --preview` | 启用 select 范围内的 preview 规则 |
| `seiso check --statistics` | 按规则统计违规数，并列出全部 suppression 及理由 |
| `seiso check --output-format <fmt>` | `text`（默认）、`concise`、`json`、`sarif`、`github` |
| `seiso check --stdin-filename <PATH>` | 从 stdin 读内容，在本次检查中替代磁盘上的 PATH |
| `seiso check --no-cache` | 不读也不写缓存 |
| `seiso check --exit-zero` | 有规则违规时也返回 0；检查不完整时仍返回 2 |
| `seiso rule <CODE>`、`seiso rule --all` | 打印规则说明 |
| `seiso policy` | 输出生效后的策略：每个文件的 kind 与启用的规则、ignore 和 suppression 汇总 |
| `seiso init` | 生成配置文件，并根据目录结构建议 kind 映射 |
| `seiso index --dump` | 输出全仓索引，用于调试跨文件规则 |
| `seiso hook claude-code` | Claude Code hook 适配器（见「集成」） |

### 输出

默认的 text 格式带源码片段和处理建议（示例中的 DUP001 来自 preview 规则）：

```text
docs/guides/setup.md:14:1: RAT002 howto 页的标题在论证设计选择：“为什么选择 Redis”
   |
14 | ## 为什么选择 Redis
   |
   = 建议：howto 只写操作步骤；设计理由放进 ADR，这里留一行链接

docs/guides/deploy.md:40:1: DUP001 这里列出的 7 个标识符，也全部列在 docs/reference/config.md:12
   = 建议：如果两处描述的是同一组设置，保留 reference 中的一处，这里改成链接

Found 2 errors.
```

`concise` 每条诊断一行，末尾附一句修改建议，给 agent 读。`json` 的字段对齐 ruff：`code`、`message`、`filename`、`location`、`end_location`、`fix`、`url`，另加 `related`，列出跨文件规则涉及的其他位置。

| 退出码 | 含义 |
| --- | --- |
| 0 | 没有违规；或使用了 `--exit-zero` 且检查完整 |
| 1 | 有规则违规，且检查完整 |
| 2 | 工具错误或检查不完整：配置无效、参数错误、文件读取失败、内部错误。已经得到的诊断仍会输出 |

## 集成

agent hook 负责编辑后的即时反馈，最终门禁由提交前检查和 CI 负责。诊断自带修改建议，agent 不需要额外加载任何 skill 或 prompt。

### Claude Code hook

在 `.claude/settings.json` 里注册 PostToolUse hook：

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [{ "type": "command", "command": "seiso hook claude-code" }]
      }
    ]
  }
}
```

`seiso hook claude-code` 从 stdin 读取 hook 的 JSON 输入，取出被修改的文件路径，按带路径检查的语义运行；不是 .md 就直接退出。`seiso check` 的退出码是 seiso 自己的协议，适配器负责换成 Claude Code 的约定：

| seiso check | 适配器退出码 | Claude Code 的表现 |
| --- | --- | --- |
| 0 | 0 | 无反馈 |
| 1：有违规 | 2，`concise` 诊断写入 stderr | 诊断交给 agent |
| 2：工具错误或检查不完整 | 1，错误信息写入 stderr | 作为非阻塞错误显示给用户，不打断 agent |

覆盖范围有限：matcher 只覆盖 Write 和 Edit 工具，通过 Bash 或其他进程写入的文件不会触发；PostToolUse 也不会撤销已经完成的编辑。漏掉的写入由提交前检查和 CI 兜底。

其他 agent（Codex CLI、Cursor 等）的 hook 协议各不相同，适配器在 M4 按需求逐个添加。

### CI 与提交前检查

| 入口 | 做法 |
| --- | --- |
| pre-commit | seiso 仓库提供 `.pre-commit-hooks.yaml`，hook id 为 `seiso`，只对 Markdown 文件触发 |
| GitHub Actions | `uvx seiso check --output-format github`，违规显示为 PR 行内注释；SARIF 可上传到 code scanning |
| 策略变更 | 变更配置时在 base 和 head 上各运行一次 `seiso policy` 并比较，随变更审阅差异；建议把 seiso 配置文件加入 CODEOWNERS |
| 其他 CI | 直接用 `seiso check` 的退出码做门禁 |

### 编辑器

M4 提供 `seiso server`（LSP），在编辑器里实时显示诊断；VS Code 扩展只是它的一层薄封装。

## 质量保障

一条规则能不能默认启用，看它在没有参与调参的真实文档上的表现；整套测试体系围绕这一点搭建。

### 测试分层

| 层级 | 做法 | 守住什么 |
| --- | --- | --- |
| 规则 fixture | 每条规则一个目录，含应命中和不应命中的样例；跨文件规则的样例是一个小型仓库 | 规则行为 |
| 快照测试 | 用 insta 记录每个 fixture 的完整诊断输出，输出变化需要在 review 中确认 | 无意的行为变化 |
| 文档示例 | 规则说明里的每个“示例”和“改成”都作为 fixture 运行 | 说明文档与实际行为一致 |
| 确定性测试 | 同一快照在冷缓存、热缓存、禁用缓存下各跑一次并打乱文件顺序，输出逐字节一致；带路径检查的结果等于全量结果按报告范围过滤 | 缓存状态和检查路径不影响结果 |
| 模糊测试 | cargo-fuzz 覆盖解析和文档模型转换 | 任何输入都不 panic |
| 性能基准 | 手动运行基准仓库和压力样例，可选择 Git ref 对比 | 速度目标 |

### 首批回归场景

这些场景在开工后最先写成测试，覆盖「执行语义」里最容易出错的约定。

| 场景 | 预期 |
| --- | --- |
| 同一快照分别用冷缓存、热缓存、禁用缓存检查 | 输出逐字节一致 |
| 文件内容不变，只移动目录 | kind 和相对链接按新路径重新计算 |
| 链接目标被删除，或目标标题改名 | 来源文件没有改动，也能报出 LNK001 或 LNK002 |
| 只检查被改名标题所在的文件 | 引用它的其他文件中的 LNK002 出现在报告里 |
| preview 规则未启用，但文件里有它的 suppression | 不报 SUP002，不删除 |
| 某个文件读取失败，跨文件检查不完整 | 跨文件规则的 suppression 记为未判定；退出码为 2 |
| 修改 canonical 文件后，另一文件与它重复 | 按报告范围返回另一文件中的 DUP001 |
| 同一文档的中英文版本包含相同字段 | 属于不同比较域，不报 DUP001 |
| 多条 `[[kinds]]` 同时命中 | 最后一条生效 |
| frontmatter 声明 `kind: generated` | 报 KND002，按 kind 无法确定处理，不会跳过检查 |
| agent 按诊断修复 fixture | 通过检查，且未被诊断涉及的标识符、链接和数字全部保留 |

### 评估语料

- **组成。** 首批约 30 个公开项目的文档，以开源项目和英文为主，覆盖中文、日文及 agent 工具项目；具体来源和许可见[语料选择](../corpus/docs/selection.md)。
- **固定版本。** 语料清单、获取工具和验收记录放在本仓库的 `corpus/` 目录，每个项目锁定到具体 commit 和内容哈希，结果可复现；下载的原文缓存不入 Git。
- **划分。** 按仓库分成调参集和留出集，比例约 2 : 1。阈值只在调参集上调整，规则能否升级只看留出集；每个大版本补充新仓库进入留出集。
- **标注。** 语料上的每条诊断标为命中或误报。RAT、ORD、MIX 这类结构规则另需抽样标注 section 类型，用来估计漏报，也为「后续：判断层」准备校准数据。
- **报告方式。** 精度 = 命中 ÷（命中 + 误报），按规则分别报告，并按语言和主要 kind 拆开，同时披露样本数。漏报只报告、不设门槛：一条规则宁可少报，也不能乱报。

### 生态回归

在里程碑验收、发布前或大幅修改规则与解析器时，手动运行评估语料，审阅新增、消失和变化的诊断。报告保存在 workflow 摘要与产物中；操作方式见[开发指南](development.md#performance-and-ecosystem-checks)。

### 使用噪声与可理解性

- **编辑回放。** 重放语料仓库真实的文档提交历史，统计每 100 次文档提交里被错误拦截的次数。单条诊断的精度看不出这种噪声，启发式规则升级前必须看这项。
- **修复测试。** 让一个不加载任何 skill 的 agent 只凭 `concise` 输出修复 fixture。“改对”要同时满足三点：通过检查；原文中未被诊断涉及的标识符、链接和数字全部保留（自动比对）；抽样人工复核确认语义没有丢失。比例偏低的规则优先改写诊断文案和说明文档。

### 性能基准

| 场景 | 目标 |
| --- | --- |
| 带路径检查，hook 模式，完整工作区热缓存，含进程启动 | < 150 ms |
| 全量检查，热缓存 | < 500 ms |
| 全量检查，冷缓存 | < 1 s |

测量条件：基准仓库有 1,000 个 Markdown 文件、合计约 10 MB，其中包含大量重复模板和相似段落的压力样例；使用默认规则集；以 `--output-format concise` 输出到文件；在 CI 的标准 Linux runner 上测量，结果连同 CPU 型号和核数一起记录。

preview 规则单独计时，不计入上述目标。DUP003 必须先做候选筛选（例如 MinHash 分桶），不能对段落两两全量比较。

## 实施路线图

| 阶段 | 交付物 | 退出门槛 |
| --- | --- | --- |
| M0 地基 | Cargo workspace；markdown-rs → 文档模型，含片段类型与源码映射；配置发现与合并；诊断数据结构，text 与 JSON 输出；insta 快照测试框架；在 crates.io、PyPI、npm 占名并发布 0.0.0 | 评估语料全部文件解析无 panic；中日英混排样例的源码位置正确；两次运行输出逐字节一致 |

| M2 跨文件规则 · 0.2 | 先按「执行语义」实现工作区、索引、缓存和报告范围，再实现阶段为 M2 的 7 条规则；SUP002 的安全修复；`--statistics`、SARIF 与 GitHub 注释输出；手动语料回归与性能验收 | 首批回归场景全部通过；性能基准达标；DUP、OWN 各规则在留出集上有精度报告 |

## 风险与未决问题

最大的风险是诊断比证据说得更确定：agent 会照着诊断直接改，所以各项应对都围绕“宁可少报，措辞不越过证据”。

| 风险 | 后果 | 应对 |
| --- | --- | --- |
| 诊断的语气强于证据：依据不足却建议删除或迁移 | agent 照做后丢失必要内容 | 诊断只陈述观察到的事实，建议写成条件式；修复测试检查内容是否保留 |
| 启发式规则误报高 | 用户关掉整个工具 | 启发式规则默认留在 preview；升级要求留出集精度和使用噪声都达标 |
| 缓存或检查路径导致结果不一致 | 同一仓库在不同场景下结论不同 | 缓存只存内容推导的数据；带路径检查定义为全量结果的过滤；首批回归场景覆盖 |
| 老仓库补 kind 的成本高 | 采用门槛高 | 路径映射批量指定；`seiso init` 按目录结构建议映射；KND001 可以按目录分批启用 |
| agent 为了通过检查而绕过规则：换同义词、滥用 suppression、把文件映射成 generated、扩大 ignore | 规则形同虚设 | 规则尽量查结构而不是措辞；suppression 必须写理由；generated 只能在配置中指定；`seiso policy` 在 CI 中单独展示策略变化 |
| 中日文处理：没有空格分词、全角标点、标题锚点规则不同 | 中日文误报或漏报 | 短语直接在字符上匹配；长度阈值按字符数计；源码位置映射和锚点算法用中日文语料单独测试 |
| markdown-rs 的速度或维护状态不达预期 | 速度目标落空 | 规则只依赖文档模型；必要时换成 comrak 或 pulldown-cmark，规则代码不受影响 |
| 诊断和说明不够直白 | 用户或 agent 看不懂就不改，或直接用 suppression 绕过 | 每条诊断附修改建议；说明文档用固定结构；用修复测试检验（见「质量保障」） |

## 后续：判断层

判断层不进第一版。等 M3 的 section 标注完成后，再评估 Jev 这类分类模型能否把 RAT、MIX 的精度提上去。

[Jev](https://openrouter.ai/typesafe/jev-1.13) 是 TypeSafe 在 2026 年 9 月发布的模型，不生成文本，只返回带概率的类型化答案：是否、多选一、分级。这正好对应 seiso 最弱的一环：判断一个 section 属于步骤、参考还是论证。

- **只做分类。** Jev 只替换启发式 section 分类器；规则报不报错，仍由代码按阈值判定。
- **流水线。** 确定性预筛找出候选段落 → Jev 回答“这段属于步骤、参考、论证、背景还是其他” → 代码按阈值判定。阈值用 M3 的标注集校准，Jev 的 confidence 不能直接当阈值用（[Braintrust](https://www.braintrust.dev/blog/evaluate-agent-responses-with-jev)、[HoneyHive](https://www.honeyhive.ai/blog/how-to-use-typesafe-ais-jev-as-an-llm-judge)）。
- **接口。** 新增 `seiso_judge` crate，定义 classifier backend trait：默认用启发式，Jev 作为可选 backend，通过 `--judge` 或配置 `[judge] backend = "jev"` 启用。
- **可复现。** 分两种模式：评估模式调用模型并记录结果；冻结模式只读取已经接受的结果，缺失时记为未判定、不产生诊断，CI 使用冻结模式。结果的 key 覆盖请求的全部输入：段落内容、section 标题、kind、上下文、问题文本、backend 与模型版本。
- **进入条件。** 在同一标注集上，Jev 的精度明显高于启发式分类器，成本和延迟也可以接受。
